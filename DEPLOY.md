# Deployment Guide

The site is a **prerendered static Angular app** on Firebase Hosting. There is no
runtime Node/SSR server and no Cloud Function — every route is either a real HTML
file produced at build time or falls back to the client shell.

## What gets deployed

| Item             | Value                          |
| ---------------- | ------------------------------ |
| Firebase project | `serhii-deineko`               |
| Build command    | `yarn build`                   |
| Uploaded folder  | `dist/browser`                 |
| Live URL         | https://serhii.com.pl          |
| Firebase default | https://serhii-deineko.web.app |

`yarn build` is `ng build` with the default `production` configuration, which
prerenders the home page and every project page into static HTML.

## Deployment

Deployment is manual. Nothing happens on push — there is no active GitHub
Actions workflow.

```bash
firebase login
yarn deploy
```

`yarn deploy` is `ng build && firebase deploy --only hosting`. It does **not**
run the lint or test gates, so run them yourself before shipping:

```bash
yarn lint && yarn test:ci
```

`public/` must stay committed — it holds every image, icon and the CV PDF.

## Re-enabling the CI pipeline

The two workflows are kept verbatim in `.github/workflows.disabled/`. GitHub only
reads `.github/workflows/`, so they never trigger while the directory is named
this way. To turn them back on:

```bash
git mv .github/workflows.disabled .github/workflows
```

`firebase-hosting-merge.yml` runs on push to `main` (install → lint → test →
build → deploy to the `live` channel). `firebase-hosting-pull-request.yml` runs
the same gates plus a formatting check on every pull request, then deploys to a
temporary preview channel whose URL is posted as a PR comment; previews expire
after 7 days and fork pull requests are skipped so secrets are never exposed.

Both were generated by `firebase init hosting:github` and authenticate with the
repo secret `FIREBASE_SERVICE_ACCOUNT_SERHII_DEINEKO`, which has to exist in the
repository before either can deploy. The service account needs the **Firebase
Hosting Admin** role.

## Local preview of the real production output

```bash
yarn preview
```

Builds and serves the exact deployable folder through the Firebase Hosting
emulator on http://127.0.0.1:5000, applying the real rewrites, redirects and
headers from `firebase.json`.

## Routing (why direct links never 404)

Angular is a single-page app, so the host must answer for URLs that have no file
on disk. Three layers cover this:

1. **Prerendered files** — `/` and each `/project/<id>` are written to disk as
   `index.html` / `project/<id>/index.html` and served directly. Crawlers and
   social scrapers get fully rendered markup.
2. **Rewrite fallback** — `firebase.json` rewrites `**` to `/index.csr.html`, the
   empty client shell. Any other URL (a refresh, a shared deep link, a route
   added later) returns **200 + the shell**, and the Angular router takes over.
3. **In-app catch-all** — the `**` route in `app.routes.ts` redirects unknown
   paths to the home page.

The fallback deliberately targets `index.csr.html`, not `index.html`: the latter
contains the prerendered home page, which would flash the wrong content and break
hydration on a project URL.

`trailingSlash: false` keeps one canonical URL per page — `/project/foo/` issues a
301 to `/project/foo`, matching the canonical tags emitted by `SeoService`.

## Adding a project page

Prerendered params come from `getPrerenderParams` in `app.routes.server.ts`, which
reads project ids from `src/assets/i18n/en.json` and keeps only ids present in
`PROJECTS_DEFINITIONS`. A project missing from either source still works as a
client-rendered page, but gets no prerendered HTML.

**Add the new URL to `public/sitemap.xml` as well** — that file is maintained by
hand and copied to the output as-is.

## Docker (alternative host)

```bash
docker build -t portfolio .
docker run -p 8080:80 portfolio
```

`nginx.conf` mirrors the Firebase behaviour: `try_files $uri $uri/index.html
/index.csr.html`, immutable caching for hashed assets, revalidation for HTML.

## Security notes

- No API keys or secrets are bundled in the client. The app calls no backend of
  its own — it only loads its own i18n JSON from the same origin.
- Third-party requests are limited to Google Fonts (stylesheet + font files) and
  the Umami analytics script on `cloud.umami.is`. Umami is cookieless and stores
  no personal data, so the site needs no consent banner.
- Hosting sends `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`,
  `Permissions-Policy` and HSTS on every response.
